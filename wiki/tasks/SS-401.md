# Validation service

## Summary

The core validation logic, called by the scheduled trigger in SS-402: for a given repository, first
atomically change its status from `"pending"` to `"in progress"` ([AD-15](../architecture-invariants.md#ad-15), [FR-BE9](../requirements.md#fr-be9)). Then for each skill
in that repo, fetch the content at the stored commit hash from GitHub (always fresh, never cached — [NFR3](../requirements.md#nfr3)),
call the Anthropic SDK to check it for security/convention issues (critical) and best-practice
gaps (non-critical) ([FR-BE5](../requirements.md#fr-be5)), and write the result as `valid: boolean` ([FR-BE7](../requirements.md#fr-be7))
and a `findings` array (`{ severity: 'critical' | 'recommendation', message: string }[]`) on that
skill's Firestore doc. `valid` is `false` if any critical findings exist, `true` otherwise.
After all skills are processed, call `repositories-store.ts`'s `recalculateValidationStatus(repoId)`
([AD-13](../architecture-invariants.md#ad-13)) synchronously, in the same invocation, to roll that up onto the repository
doc: `"validated"` only if every skill has `valid: true`, otherwise `"failed"` ([FR-BE8](../requirements.md#fr-be8));
`"pending"` skills not yet checked don't affect the calculation. This function touches
validation status only, never install count — the counterpart to SS-504's
`recalculateInstallCount` call, per [AD-11](../architecture-invariants.md#ad-11)/[AD-13](../architecture-invariants.md#ad-13)'s one-field-per-helper split.

## Unit test requirements

- Before processing skills, the repo status is atomically changed from `"pending"` to `"in progress"`.
- Given a mocked Anthropic response with at least one critical finding, the skill's
  `valid` field becomes `false` and both severities are stored in `findings`.
- Given a mocked response with only recommendations, the skill's `valid` field becomes `true`.
- `recalculateValidationStatus` is called after all skills are processed, and the
  repository-level status it produces is `"validated"` only if all skills have `valid: true`.
- The GitHub content fetch uses the commit hash stored in the repository document,
  not a cached copy of the content.
- This function never writes a skill's or repository's `installCount` field — only
  `valid`/`findings` and repo `validationStatus`.

## Integration test requirements

- Running the service against the Firestore emulator with a stubbed Anthropic client
  and a stubbed GitHub fetch persists the expected `valid: boolean`, `findings` array, and calculated
  statuses at both skill and repository level.
- Repo transitions from `"pending"` → `"in progress"` → `"validated"` or `"failed"`.
