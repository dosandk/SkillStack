# `scanRepository` Cloud Function

## Summary

Implement the skill-discovery algorithm ([AD-6](../architecture-invariants.md#ad-6)) as its own Cloud Function: given a
GitHub repo URL (+ optional `--skill` list), walk its tree via the GitHub API using backend's token (no rate limits), match `SKILL.md` up to nesting depth
3 ([FR-CLI2](../requirements.md#fr-cli2), [NFR4](../requirements.md#nfr4)), and take the whole matched directory regardless of its own depth.
Plain deterministic code — no LLM involved. In the same
call, check Firestore (via SS-101's store) for whether the repository already exists,
its stored commit hash, and validation status (including `"in progress"` per [FR-BE6](../requirements.md#fr-be6)). Returns unified response with metadata AND file content ([AD-6](../architecture-invariants.md#ad-6), [AD-7](../architecture-invariants.md#ad-7)): skill list/paths, file content (blobs), commit hash, per-skill `valid: boolean` status, repo-level validation status, README blurb. File content is included in the response but never persisted in Firestore (only commit hash is stored — [NFR2](../requirements.md#nfr2)). This function is shared: CLI and the web favorites UI call it.

**Four-branch logic:**
1. Repo unknown → `known: false`, include discovered skills + file content
2. Same commit → `known: true`, include validation statuses from Firestore
3. Different commit, status not `"in progress"` → `known: true`, commitHash differs, include validation statuses
4. Different commit, status `"in progress"` → `known: true`, `repoValidationStatus: "in progress"`, include skills + file content

**Response schema** (per [AD-5](../architecture-invariants.md#ad-5) documented-by-example):

```json
{
  "repoSlug": "owner/repo-name",
  "commitHash": "a1b2c3d4...",
  "defaultBranch": "main",
  "readmeBlurb": "Short description from README",
  "known": true,
  "repoValidationStatus": "validated",
  "skills": [
    {
      "name": "firebase-basics",
      "path": "skills/firebase-basics",
      "valid": true,
      "files": [
        {
          "path": "skills/firebase-basics/SKILL.md",
          "content": "base64-encoded-content..."
        },
        {
          "path": "skills/firebase-basics/example.ts",
          "content": "base64-encoded-content..."
        }
      ]
    }
  ]
}
```

## Unit test requirements

- Given a mocked GitHub tree response, the discovery function returns every path whose
  final segment is `SKILL.md` at depth ≤ 3, and none deeper.
- Once a `SKILL.md` match is found, the returned skill entry includes all files in that
  directory (any sub-depth) with base64-encoded content.
- File content is fetched via GitHub blobs API and included in the response structure.
- A repo with no `SKILL.md` within 3 levels returns an empty skill list, not an error.
- The Firestore-existence check returns `{ known: false }` for an unseen repo.
- For a known repo: same commit → include `valid: boolean` + `repoValidationStatus`.
- For a known repo: different commit + status not `"in progress"` → include validation statuses + different commitHash.
- For a known repo: different commit + status `"in progress"` → return `repoValidationStatus: "in progress"`.

## Integration test requirements

- Calling the function against a stubbed GitHub API and the Firestore emulator returns
  the expected skill list with file content plus the correct four-branch response (unknown, same commit, different commit, in-progress).
