# Repository & skills schema + validated-only query

## Summary

Replace the current minimal `repositorySchema` in `functions/src/services/repositories-store.ts`
(`repositoryPath`, `author`, `commitHash` only) with the full shape: a `repositories` doc (owner, repo reference, commit hash,
README-derived description, calculated validation status including `"in progress"`, calculated install count,
timestamps) and a `skills` subcollection (name, **path** (relative path in repo), `valid: boolean` field, `findings` array —
`{ severity: 'critical' | 'recommendation', message: string }[]` — install count,
timestamps). Add a query function that returns only docs whose calculated status is
`"validated"`, for the public catalog ([FR-UI1](../requirements.md#fr-ui1)). No skill file
content is ever stored — commit hash and path only ([FR-BE2](../requirements.md#fr-be2), [NFR2](../requirements.md#nfr2)). This is the single schema every other
story's backend task reads/writes through ([AD-1](../architecture-invariants.md#ad-1), [AD-2](../architecture-invariants.md#ad-2)). This is also where the
per-field aggregation helpers live: `recalculateInstallCount(repoId)` ([AD-11](../architecture-invariants.md#ad-11), used by
SS-504) and `recalculateValidationStatus(repoId)` ([AD-13](../architecture-invariants.md#ad-13), used by SS-401) — each
recomputes exactly one calculated field from the current `skills` subcollection, never
both at once. The repository validation status enum is `"pending" | "in progress" | "validated" | "failed"` ([FR-BE6](../requirements.md#fr-be6)).

## Unit test requirements

- The repository schema accepts a fully-populated payload with `"in progress"` status and rejects one missing a
  required field or with a wrong-typed field.
- The skill schema accepts `valid: boolean` field, the `path` field (relative path in repo), accepts a payload with an empty `findings` array (not yet validated)
  and one with populated findings, and rejects a finding missing `severity` or `message`.
- Server-side timestamp assignment overrides any client-supplied `created`/`updated`.
- The validated-only query filter excludes `"pending"`, `"in progress"`, and `"failed"` documents.

## Integration test requirements

- Writing a repository + skills subcollection via the store against the Firestore
  emulator persists every field (including skill `path`) and no raw skill file content.
- Listing against the emulator with the public filter returns only
  calculated-status = `"validated"` documents.
