## ADR-10 — Auth-token propagation via `backendService.setAuthTokenProvider` injection

**Status:** Accepted

**Context.** `shared/firebase-cloude-api/` is a transport-only gateway consumed by
both the browser client (which signs users in with the Firebase Web SDK) and the
CLI (which never signs in through Firebase). Protected endpoints — favorites,
share-link creation, shared-collection reads — need an ID token on the request,
but `shared/` cannot import the Firebase Web SDK without pulling browser-only
dependencies into the CLI bundle and breaking ADR-4's "one gateway, two
consumers" contract.

**Decision.** `backendService` in `shared/firebase-cloude-api/index.ts` exposes a
`setAuthTokenProvider(provider: () => Promise<string | null>)` injection point.
The client's `AuthContext` (`client/src/context/AuthContext.tsx`) registers a
provider that returns the current Firebase user's ID token; the CLI never
registers one. On protected calls, the gateway invokes the provider and attaches
the returned token as `Authorization: Bearer <token>`; a `null` result is sent
as an unauthenticated request. `client/src/lib/api.ts` remains a thin re-export
of the shared service.

**Consequences.**

- `shared/` stays free of any identity SDK dependency; the CLI bundle does not
  pay for Firebase Auth.
- Auth wiring lives in exactly one place per consumer (the client's
  `AuthContext`) instead of being repeated per call site.
- Cost: two runtime states now exist (provider registered / not registered) that
  the gateway cannot distinguish at compile time; a protected request from the
  CLI is a bug only the backend can reject.
