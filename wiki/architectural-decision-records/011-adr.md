## ADR-11 — Repository detail page reuses `repository.skills` from the list response

**Status:** Accepted

**Context.** The Favorites & Sharing work added a repository detail page under
`client/src/pages/RepositoryDetailPage/`. The list endpoint already returns each
repository's `skills[]` array — `RepositoryList` uses that same field to show
skill names in each row. A dedicated "get repository by id" endpoint on
`functions/src/services/repositories-store.ts` would refetch data the client
just downloaded.

**Decision.** The detail page selects its repository (including `skills`) from
the same list response the browse page already fetched, routed through the
existing client state. No `apiGetRepositoryById` endpoint is added; the store
gains no new lookup. `repository.skills` remains the single source for both
list-row and detail views.

**Consequences.**

- Smaller blast radius: no new Handler / Domain / Store trio (ADR-3), no new
  gateway method in `shared/`, no new cache path to invalidate on favorite
  toggles.
- The two views stay consistent by construction — they read the same field of
  the same object.
- Cost: navigating directly to a detail URL requires the list to be loaded
  first; the detail page is not self-sufficient and cannot render without the
  preceding list request.
