## ADR-14 — `AppLink` / `AppNavButton` wrappers bridge the ELEKS UI Link/Button typing gap

**Status:** Accepted

**Context.** The Favorites & Sharing work wires react-router navigation into
ELEKS UI `Link` and `Button`. Both components support MUI's `component` prop
for polymorphism, but the vendored `@eleks-ui/components` re-exports use MUI's
non-generic default `Props`, which drops the `component`-driven prop inference.
Passing `component={RouterLink}` together with `to="..."` fails to typecheck at
every call site (`AppHeader`, `RepositoryList`, `FavoritesPage`, …), so each
call site would otherwise need its own type cast.

**Decision.** Two thin wrappers — `AppLink` and `AppNavButton`, in
`client/src/components/RouterLink/` — render the ELEKS UI `Link` / `Button`
with `component={RouterLink}` and expose a router-aware prop surface. Each
wrapper contains the one necessary type cast; consumers (`AppHeader`,
`RepositoryList`, `FavoritesPage`) use the wrappers instead of casting inline.

**Consequences.**

- One cast per component instead of one cast per call site; upgrading the
  vendored ELEKS UI types (ADR-8) touches these two wrappers, not every
  navigation link/button.
- Router integration is discoverable — reviewers find it in `RouterLink/`
  rather than scattered across pages.
- Cost: two more indirection components in the client tree; any prop the
  underlying ELEKS UI component grows must be re-surfaced through the wrapper
  before call sites can use it.
