## ADR-13 — Single `create-share-link` endpoint covers "share everything" and "share one repo"

**Status:** Accepted

**Context.** The Favorites page (`client/src/pages/FavoritesPage/`) exposes two
share buttons — "share all my favorites" and "share this repo's favorited
skills". Both produce a public shared-collection link with the same underlying
structure. Modeling them as two endpoints
(`create-share-link-all` + `create-share-link-repo`) would duplicate validation,
persistence, and error handling for a scope difference the payload already
expresses.

**Decision.** A single `apiCreateShareLink`
(`functions/src/functions/create-share-link/function.ts`) accepts an optional
`repoIds` field. Omitting it (or passing an empty array) shares the caller's
full favorites; passing `repoIds: [id]` shares that repo's favorited skills
only. The Favorites page surfaces the same endpoint through two buttons that
differ only in the payload they send.

**Consequences.**

- One Handler / Domain / Store path to test, validate, and evolve; new
  "share subset" variants (e.g. by skill id) become payload changes, not new
  endpoints.
- The two UI buttons stay thin — pure input shaping over a shared contract.
- Cost: the endpoint's input has a conditional shape (`repoIds` optional with
  semantic meaning), which the domain layer must validate explicitly rather
  than relying on separate typed endpoints to enforce intent.
