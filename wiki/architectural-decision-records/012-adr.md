## ADR-12 — Favorites mutation endpoints return the full enriched favorites list

**Status:** Accepted

**Context.** `client/src/hooks/useFavorites.ts` renders both the Favorites page
and the favorite toggles on repo/skill cards. After a mutation — add repo, add
skill, remove — the UI must reflect the new list, including enriched fields
(repository metadata, skill descriptions) the client does not compute itself.
The REST-shaped alternative is a bare acknowledgement followed by a second
"list favorites" request.

**Decision.** `apiAddRepoFavorite`, `apiAddSkillFavorite`, and
`apiRemoveFavorite` (`functions/src/functions/{add-repo-favorite,add-skill-favorite,remove-favorite}/function.ts`)
each return the caller's full enriched favorites list as their response body.
`useFavorites` replaces local state with the response and never issues a
follow-up read on mutation.

**Consequences.**

- One request per user action; the UI updates from a single authoritative
  payload without a stale-then-refresh flicker.
- Enrichment stays on the backend — the client never re-derives favorite shape,
  keeping the backend the sole source of truth (ADR-5).
- Cost: every mutation pays for a full list read on the server, and payload
  size grows with the user's favorites count instead of staying O(1) per
  mutation.
