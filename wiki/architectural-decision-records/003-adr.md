## ADR-3 — Three-layer backend: Handler → Domain → Store

**Status:** Accepted

**Context.** Backend code tends to entangle HTTP handling, business rules, and
database access, which makes every unit have several reasons to change and blocks
unit-testing the rules in isolation.

**Decision.** Inside `functions/`, split every capability into three layers with one
reason to change each:

- **Handler** (`functions/src/functions/*/index.ts`) — transport only: parse request,
  call one domain function, map result/errors to HTTP status codes. `index.ts` is the
  only file that exports Firebase entry points; `admin.initializeApp()` runs there.
- **Domain** (`functions/src/functions/*/function.ts`) — business rules and Zod
  validation; knows nothing about HTTP or Firestore.
- **Store** (`functions/src/services/repositories-store.ts`) — the sole Firestore
  access layer; owns collection names, document shapes, and schemas.

A request travels Handler → Domain → Store and back.

**Consequences.**

- Domain rules are unit-testable without HTTP or a database.
- Adds boilerplate (three files per capability) that is deliberately accepted.
